It's built using a Rust parser/combinator crate called _nom_. It's fantastic. Except for the part where the error messages are cryptic as hell. For example, this code uses nom's `alt` feature to try two different ways to parse an input:

== filter highlight("rust") == include dir() + "/examples.inc/default_errors/src/main.rs" == endfilter Both parsers fail since neither of their patterns (i.e. "xxx" or "yyy") match the "target" text of the input. nom throws an error when parsing fails. Here's what it looks like for this example: == filter output() == include dir() + "/examples.inc/default_errors/output.txt" == endfilter - The `input: "target"` shows us what the parser attempted to process.j - The `code: Tag` lets us know that the error was generated because on of the attempts to use a `.tag()` failed. Critically, it doesn't tell us which one of them failed. Figuring out the issue in this example is no big deal. It's quick to see that neither the `alfa` nor the `bravo` parsers match the `target` input that was passed to them. Things are rarely so obvious in more complicated parsers. Each branch of the `alt` could call multiple child parers that call ones further down the tree, etc. It doesn't take long to cross a threshold where figuring out where an error occurred is a non-trivial task. I used to use a crate called _nom_supreme_ on top of nom. It provided errors with more details about where they came from. Unfortunately, nom_supreme doesn't work with nom's most recent major version update. That's where _nom_locate_ enters the scene. ## Locating Errors nom_locate works by adding a `LocatedSpan` struct to the mix. Your input goes inside and gets passed around by it. That'll help demonstrate the error output of this report function: == filter highlight("rust", file_name="src/report.rs") == include dir() + "/examples.inc/locate_report/src/report.rs" == endfilter Here's the overview of how it works: - The `type ResultHolder<'a>` lines just keep us from having to put the entire signature in the function definition. - The `result.finish()` call on line 14 combines a couple of different nom error types so they can be matched in a single call. - Line 15 prints a succsss message of everything parsed properly. - The `Err` branch that starts on line 16 does a bunch of formatting to print out a nice error message. - The `e.input` field from the error contains the LocatedSpan struct that was passed in to the report. `e.input.extra` on line 19 pulls the value with the name of the parser we added in those functions. `e.input.location_line()` on line 20 gets the line number from the original input where the error occured (which will be 2 in our case since first_parser got us to the second line). `e.input.get_utf8_column()` on line 21 give us the column of the `.location_line()` where the error starts. (There's a similar `.get_column()` that can be used if all you've got is ASCII, but I don't mess with that.) - Lines 23-25 contain `e.input.get_line_beginning()` that pulls in the full line that the error occured on. It comes in as `&[u8]` so the `.to_vec()` and `String::from_utf8()` calls are used to turn it into text. - The rest of the funciton is the formatting that shows the line where the error occurred and puts a `^` under the column where the error started.
