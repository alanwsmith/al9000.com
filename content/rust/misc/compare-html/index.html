== extends "/templates.inc/switches/default.html" == block toml title = "Compare HTML Fragments in Rust to See if They Match" created = 2026-08-18T18:53:22-04:00 status = "done" id = "01/n8/9r/k2" == endblock == block main == filter md I'm working on extracting [NeoDoc](https://neodoc.style) from my static site generator to pitch the format as an option for the [Atmosphere](https://atmosphere.community/) of [AT Proto](https://atproto.com/). Part of that process is making an explicit spec for HTML output. The goal being to avoid a Markdown type situation where different parsers have different features that produces different outputs from the same input. Validating the output is a little tricky. The simplest way would be to just compare to strings. ``` is test the same as: test yes? you're good ``` The problem is whitespace. Take these two snippets for example: ```
test
``` and ```
test
``` The only difference in them is the `strong` tag has a couple spaces in front of it in the second sample. Both samples produce the exact same thing in the browser. And, for testing purposes, they should be considered as matching. But, thanks to the whitespace, the strings are different. So, the test would fail. I've done simple testing before where I just yoinked all the spaces to collapse everything. That works great, as long as you don't need to run tests that confirm what space that should show up does. NeoDoc has some of those tests. I'm using a rust crate called [scraper](https://docs.rs/scraper/latest/scraper/) to work around that. It parses HTML that can be compared more abstractly. This is how I'm using it: == filter highlight("rust", "src/main.rs") == include dir() + "/src/main.rs" == endfilter with this Cargo.toml: == filter highlight("rust", "Cargo.toml") == include dir() + "/Cargo.toml" == endfilter which produces this: == filter highlight("txt", class="code-block no-buttons") == include dir() + "/output.inc.txt" == endfilter The whitespace in the middle of the `h1` element gets disregarded. So does the order of the attributes themselves. Even though the order of the arguments is `class, id` in the `left` variable and `id, class` in the `right` the HTML still matches. This is exactly what I'm looking for since those two samples rendered the same even though their string representations are different. Test solution acquired. Back to parsing, -a
