[! extends "/templates.inc/pages/default.html" !] == block toml title = "Better nom Error Messages with nom_locate" created = 2026-08-20T14:02:00-04:00 status = "draft" id = "01/n8/eg/8r" == endblock == block content == filter md ## Parsing Parser Errors I'm extracting NeoDoc's parser from my static site generator. It's built using a Rust parser/combinator crate called "nom". It's fantastic. Except for the part where the error messages are cryptic as hell. For example, this code uses nom's `alt` feature to try three different ways to parse an input string: == filter highlight("toml") == include dir() + "/examples.inc/default_errors/Cargo.toml" == endfilter == filter highlight("rust") == include dir() + "/examples.inc/default_errors/src/main.rs" == endfilter All three parsers fail since the "target" portion of the input string doesn't match any of their patterns (i.e. "xxx", "yyy", and "zzz"). nom throws an error when parsing fails. Here's what it looks like for this example: == filter output() == include dir() + "/examples.inc/default_errors/output.txt" == endfilter - The `input: " target"` shows us that the "prelude" portion of the string got slurped up properly and only the ` target` remains. - The `code: Tag` lets us know that the error was generated because on of the attempts to use a `.tag()` failed. Critically, it doesn't tell us which one of the three failed. Figuring out the issue in this example is no big deal. It's quick to see that neither of the `alfa`, `bravo`, or `charlie` parsers match the ` target` string that was passed to them. Things are rarely so straight forward to spot in more complicated parsers. Each of the branches could call multiple child parers that call ones further down the tree, etc. It doesn't take long to cross a threshold where figuring out where an error occurred is a non-trivial task. I used to use another crate called "nom_supreme" on top of nom. It provided errors with more details about where they came from. The problem is that nom had a major version upgrade a while back. nom_supreme doesn't work with the new iteration. That's where `nom_locate` enters the scene. ## Locating Errors nom_locate works by adding a `LocatedSpan` struct to the mix. Your `&str` input gets passed around inside it.
